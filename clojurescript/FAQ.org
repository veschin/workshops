*** Зачем столько скобок?
:PROPERTIES:
:CUSTOM_ID: зачем-столько-скобок
:END:
Скобки в Clojure/ClojureScript - это не баг, а фича. Код в CLJS - это
данные (homoiconicity), что позволяет писать макросы - код, который
генерирует код во время компиляции. Как только вы привыкаете к правилам
отступов и используете правильный редактор (с paredit/parinfer), скобки
перестают быть проблемой и становятся преимуществом - вам не нужно
помнить различия между ={}=, =[]=, =()= как в других языках.

На практике современные редакторы (VSCode с Calva, IntelliJ с Cursive,
Emacs) автоматически управляют скобками, и вы их практически не
замечаете.

*** Есть ли аналог TypeScript для ClojureScript?
:PROPERTIES:
:CUSTOM_ID: есть-ли-аналог-typescript-для-clojurescript
:END:
Нет прямого аналога TypeScript, и он не нужен по нескольким причинам:

1. *Runtime validation*: В CLJS есть =clojure.spec= и =malli= -
   библиотеки для валидации данных во время выполнения, а не только
   компиляции. Вы можете проверять данные на входе/выходе функций, в
   API, в состоянии приложения.

2. *Immutable data structures*: Многие баги, которые TypeScript пытается
   предотвратить, просто невозможны в CLJS из-за неизменяемости данных.

3. *REPL-driven development*: Вы тестируете функции в REPL с реальными
   данными сразу при написании кода, что ловит ошибки раньше чем
   TypeScript.

Если вам нужна статическая типизация, есть экспериментальные проекты
(typed-clojure), но большинство разработчиков обходятся spec + REPL.

*** Сколько времени занимает изучение ClojureScript?
:PROPERTIES:
:CUSTOM_ID: сколько-времени-занимает-изучение-clojurescript
:END:
*Базовый синтаксис*: 1-2 недели для чтения и понимания кода.

*Написание простых приложений*: 1-2 месяца для уверенной работы с
Reagent/re-frame.

*Продуктивная работа*: 3-6 месяцев для комфортного написания production
кода.

*Основная сложность* не в синтаксисе (его очень мало), а в том, что
нужно "разучиться" думать императивно и объектно-ориентированно. Как
говорят: "You must unlearn what you have learned about imperative and
object-oriented paradigms".

Большинство проблем новичков связаны не с функциональным подходом, а с
незнанием =clojure.core= API и платформенных особенностей (JVM для
Clojure, JS для ClojureScript).

*** Как дебажить ClojureScript?
:PROPERTIES:
:CUSTOM_ID: как-дебажить-clojurescript
:END:
*Browser DevTools*

#+begin_src clojure
(js/console.log "debug:" value)
(js/console.table data)
#+end_src

*REPL debugging* Самый мощный способ - оценивать выражения прямо в REPL:

#+begin_src clojure
(def state (atom {:users []}))
@state  ; посмотреть текущее состояние
(swap! state assoc :debug true)  ; изменить на лету
#+end_src

*tap>* Современный способ дебага:

#+begin_src clojure
(tap> {:event :user-clicked :data user})
; Данные попадают в tap-системы (Portal, Reveal)
#+end_src

*re-frame-10x* (для re-frame приложений) - Time-travel debugging -
Просмотр всех events/effects - Diff состояний

*Source maps* Shadow-cljs автоматически генерирует source maps, поэтому
в Chrome DevTools вы видите оригинальный CLJS код, а не скомпилированный
JS.

*** Можно ли использовать npm библиотеки?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-npm-библиотеки
:END:
Да, shadow-cljs имеет first-class поддержку npm:

#+begin_src clojure
;; package.json
{
  "dependencies": {
    "react": "^18.0.0",
    "lodash": "^4.17.21"
  }
}

;; ClojureScript
(ns app.core
  (:require ["react" :as react]
            ["lodash" :as _]))

(react/createElement "div" nil "Hello")
(_.debounce my-fn 300)
#+end_src

*Interop с React компонентами:*

#+begin_src clojure
(:require ["@mui/material" :refer [Button TextField]])

(defn my-component []
  [:> Button {:variant "contained"
              :on-click #(js/alert "Clicked")}
   "Click me"])
#+end_src

Работают все npm библиотеки без исключений. Для React-компонентов есть
удобный синтаксис =[:> Component props]=.

:PROPERTIES:

*** Persistent data structures медленные?
:PROPERTIES:
:CUSTOM_ID: persistent-data-structures-медленные
:END:
*Короткий ответ*: Нет, для большинства приложений они быстрее.

*Технически*: - Persistent structures используют structural sharing -
копируется только изменённая часть дерева (O(log32 N)) - Сравнение
коллекций - O(1) благодаря hash и reference equality - Не нужно делать
defensive копии как в JS (={...obj}=)

*React/Reagent context*: - В React нужно =memo()=, =useMemo()=,
=useCallback()= для оптимизации - В Reagent structural sharing +
=identical?= проверка дают автоматическую оптимизацию без memo -
shouldComponentUpdate бесплатно благодаря immutability

*Benchmarks*: ClojureScript приложения часто быстрее чем аналоги на
React, потому что React под капотом тоже использует virtual DOM diffing,
но без гарантий immutability приходится проверять всё дерево.

Если нужна максимальная производительность, есть transients для batch
mutations: =O(1)= как у мутабельных структур, но с гарантиями
immutability после завершения.

*** Какой bundle size у ClojureScript приложений?
:PROPERTIES:
:CUSTOM_ID: какой-bundle-size-у-clojurescript-приложений
:END:
*Реальные цифры:*

Hello World с Reagent: ~250-300 KB (gzip) - React: ~40 KB -
ClojureScript runtime: ~80 KB - Reagent: ~20 KB - Google Closure
runtime: ~100 KB

Среднее production приложение: 500 KB - 1 MB (gzip)

*Важно понимать:* - Первоначальный bundle больше чем у Vue/React, но
рост замедляется благодаря отсутствию дублирования кода - Google Closure
Compiler удаляет мёртвый код агрессивнее чем Webpack/Rollup - Code
splitting работает из коробки - Для landing pages не лучший выбор, для
продуктивных SPA приложений - разница между 500 KB и 1 MB не критична

*Оптимизации:*

#+begin_src clojure
;; shadow-cljs.edn
:compiler-options {:infer-externs :auto}  ; автоматический advanced compilation
:module-hash-names true  ; для кеширования
#+end_src

*** Hot reload работает нормально?
:PROPERTIES:
:CUSTOM_ID: hot-reload-работает-нормально
:END:
*Да, и это одна из killer features ClojureScript.*

Shadow-cljs поддерживает hot reload без потери state:

#+begin_src clojure
(defonce state (atom {:count 0}))  ; defonce сохраняет state при reload

(defn component []
  [:div @state])  ; изменения компонента применяются мгновенно
#+end_src

*Почему это работает лучше чем в React:* - Функции без побочных эффектов
можно перезагружать безопасно - State в atoms/re-frame живёт независимо
от компонентов - Нет lifecycle hooks, которые нужно пересоздавать

*Fast Refresh в React vs CLJS:* - React Fast Refresh требует специальных
правил (hooks должны быть в правильном порядке, etc) - CLJS hot reload
просто работает для любых функций

Время от сохранения файла до обновления в браузере: обычно < 1 секунды.

*** Startup time какой?
:PROPERTIES:
:CUSTOM_ID: startup-time-какой
:END:
*Development:* - Первая компиляция (cold start): 10-30 секунд в
зависимости от размера проекта - Incremental компиляция: 0.5-2 секунды -
REPL startup: 5-10 секунд

*Production build:* - Small app: 30-60 секунд - Large app: 2-5 минут -
Google Closure advanced compilation медленная, но результат того стоит

*Runtime (в браузере):* - Инициализация CLJS runtime: минимальная,
незаметная - Первый рендер: сравнимо с React

*Сравнение с TypeScript/Vite:* - Development: CLJS медленнее на первом
запуске, но incremental compile сравним - Production: CLJS медленнее
(из-за Closure Compiler), но bundle меньше и оптимизированнее

Для больших команд обычно используют CI для production builds, dev
builds достаточно быстрые.

*** Есть ли поддержка SSR/SEO?
:PROPERTIES:
:CUSTOM_ID: есть-ли-поддержка-ssrseo
:END:
*Да, но это не основной use case.*

*Для SEO есть несколько подходов:*

1. *Pre-rendering* (рекомендуется)
   - Используйте prerender.io или headless Chrome для генерации статики
   - Подходит для большинства случаев
2. *Server-Side Rendering*
   - Библиотеки: reagent-server (experimental)
   - Node.js: можно рендерить CLJS на Node через shadow-cljs
   - JVM: можно использовать Clojure на бэкенде для server-side
     rendering
3. *Static Site Generation*
   - Для блогов/документации: Cryogen (Clojure SSG)

*Реальность:* Большинство CLJS приложений - это productivity apps (admin
панели, dashboards, internal tools), где SEO не критично. Для marketing
сайтов обычно используют отдельный стек (Next.js, Astro).

Если SEO критично для всего приложения - возможно, CLJS не лучший выбор.

*** Как тестировать ClojureScript код?
:PROPERTIES:
:CUSTOM_ID: как-тестировать-clojurescript-код
:END:
*Unit тесты:*

#+begin_src clojure
(ns app.core-test
  (:require [cljs.test :refer [deftest is testing]]))

(deftest addition-test
  (is (= 4 (+ 2 2))))
#+end_src

#+begin_src sh
npx shadow-cljs compile test
# или с watch
npx shadow-cljs watch test
#+end_src

*Популярные библиотеки:* - =cljs.test= - встроенная -
=clojure.test.check= - property-based testing - =day8/re-frame-test= -
для re-frame приложений

*E2E тесты:* - Cypress работает как с обычным SPA - Playwright тоже
работает

*REPL-based testing:* Многие разработчики тестируют функции прямо в
REPL:

#+begin_src clojure
(defn process-data [data]
  (tap> {:input data})  ; debug
  (->> data
       (filter valid?)
       (map transform)))

;; В REPL:
(process-data test-data)  ; сразу видим результат
#+end_src

   - Зарплаты выше среднего
   - Интересные технические задачи

*Альтернативный подход:* Не переводите всё на Clojure. Используйте его
для: - Backend API (где можно нанять JVM разработчиков и обучить
Clojure) - Internal tools - Data processing

Frontend оставьте на React/Vue/TS (больше кандидатов).

   - Быстрая обратная связь

   - "Clojure for the Brave and True" (книга)

*** Можно ли использовать ClojureScript в команде из одного человека?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-clojurescript-в-команде-из-одного-человека
:END:
*Да, и это даже лучше чем в большой команде.*

*Почему solo dev выигрывает:*

1. *Нет онбординга*
   - Не нужно обучать команду
   - Пишете как удобно вам
2. *Fullstack из коробки*
   - Один язык для frontend/backend
   - Shared code (.cljc)
   - Меньше context switching
3. *Долгосрочная стабильность*
   - Код не устаревает как JS frameworks
   - Меньше рефакторингов из-за breaking changes
4. *Производительность*
   - REPL-driven development быстрее
   - Меньше boilerplate
   - Меньше времени на настройку tooling

*Когда не стоит:* - Планируете быстро масштабировать команду - Нужно
продать продукт (а не technology) - Критично время до маркета (time to
market)

*Реальные кейсы:* Многие solo developers используют Clojure/CLJS для: -
SaaS продуктов - Internal tools - Data analysis tools - MVPs

*Recommendation:* Если вы solo и не планируете быстро расти - CLJS
отличный выбор. Если нужна команда через полгода - возможно, React/TS
безопаснее.

*** Можно ли использовать любую React библиотеку в ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-любую-react-библиотеку-в-clojurescript
:END:
*Да, любую.*

*Синтаксис:*

#+begin_src clojure
;; npm install @mui/material
(:require ["@mui/material" :refer [Button TextField Dialog]])

(defn my-form []
  [:div
   [:> TextField {:label "Name"
                  :value @name
                  :on-change #(reset! name (.. % -target -value))}]
   [:> Button {:variant "contained"
               :on-click handle-submit}
    "Submit"]])
#+end_src

*=:>= - специальный синтаксис Reagent для React компонентов.*

*Hooks (experimental):*

#+begin_src clojure
(:require ["react" :as react])

(defn use-fetch [url]
  (let [[data set-data] (react/useState nil)]
    (react/useEffect
      (fn []
        (.then (js/fetch url)
               #(.json %)
               #(set-data %)))
      #js [url])
    data))
#+end_src

*TypeScript типы:* Теряются, нужно смотреть в документацию библиотеки.

*Что работает:* - Material-UI, Ant Design, Chakra UI - React Spring,
Framer Motion (анимации) - React Query, SWR (data fetching) - Recharts,

*Что может быть сложно:* - Библиотеки с complex TypeScript types -
Генераторы кода (нужны workarounds) - Компоненты с императивным API (ref

*** Можно ли использовать Vue компоненты в ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-vue-компоненты-в-clojurescript
:END:
*Технически возможно, но не рекомендуется.*

ClojureScript обычно использует React (через Reagent), а не Vue.
Интеграция Vue компонентов потребует: 1. Подключить Vue runtime 2.
Создать мост между Vue и React/Reagent 3. Разбираться с двумя
реактивными системами

*Альтернативы:* 1. Используйте React версию компонента (большинство UI
библиотек есть для обоих) 2. Перепишите компонент на Reagent (часто
проще чем кажется) 3. Оставьте часть приложения на Vue, часть на CLJS
(микрофронтенды)

*Реальность:* Если вы хотите использовать Vue компоненты - возможно,
стоит остаться на Vue вместо миграции на CLJS.

*** Можно ли постепенно мигрировать проект на ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-постепенно-мигрировать-проект-на-clojurescript
:END:
*Да, несколько стратегий:*

*1. Новые фичи на CLJS* - Существующий код остаётся на React/Vue - Новые
компоненты пишете на Reagent - Общаются через props/events

*2. По страницам* - Главная страница - React - Admin панель -
ClojureScript - Общий state через localStorage или API

*3. Backend первым* - Переписываете API на Clojure - Frontend остаётся
React/Vue - Постепенно shared код переносите в .cljc

*4. Micro-frontends* - Разные части приложения - разные технологии -
Изоляция через iframe или Web Components

*Реальность:* Большинство компаний НЕ мигрируют существующие проекты на
CLJS. Вместо этого: - Новые проекты начинают на CLJS - Legacy остаётся
на старом стеке - Или ре-write при мажорном редизайне

*Если планируете миграцию:* - Начните с backend (Clojure легче продать
чем ClojureScript) - Доказывайте ценность на production - Только потом
переходите к frontend

*** Нужно ли переписывать backend на Clojure если используете ClojureScript?
:PROPERTIES:
:CUSTOM_ID: нужно-ли-переписывать-backend-на-clojure-если-используете-clojurescript
:END:
*Нет, не обязательно.*

*Варианты:*

*1. CLJS frontend + Node.js/Python/Java backend* - Работает нормально -
Теряете .cljc shared code - Дублируете validation/models

*2. CLJS frontend + Clojure backend* - Идеальный вариант - Shared код
(.cljc) - Одна команда, один язык

*3. CLJS frontend + любой REST/GraphQL API* - Backend может быть на чём
угодно - CLJS просто делает HTTP запросы

*Когда имеет смысл Clojure backend:* - Пишете новый проект с нуля -
Backend логика сложная (fintech, data processing) - Хотите fullstack
команду

*Когда НЕ имеет смысл:* - Backend работает отлично и менять незачем -
Команда backend не хочет учить Clojure - Backend на другом языке и
переписывать дорого

*Преимущества CLJS даже без Clojure backend:* - Immutability -
REPL-driven development - re-frame для state management - Structural
sharing для performance

Вы всё равно получаете большую часть выгоды от CLJS.

*** Зачем учить новый синтаксис если есть TypeScript?
:PROPERTIES:
:CUSTOM_ID: зачем-учить-новый-синтаксис-если-есть-typescript
:END:
*Философский ответ:* TypeScript решает проблемы JavaScript, добавляя
типы. ClojureScript решает фундаментальные проблемы программирования:
immutability, simplicity, data-oriented design.

*Практический ответ:*

*TypeScript даёт:* - Compile-time type safety - Better IDE
autocomplete - Refactoring tools

*ClojureScript даёт:* - Runtime type safety (spec/malli) - Immutability
из коробки - REPL-driven development - Меньше кода (threading macros,
destructuring) - Stable platform (код 10-летней давности работает) -
Homoiconicity (код = данные, макросы)

*Когда учить CLJS:* - Вам интересен функциональный подход - Вы устали от
JavaScript fatigue - Вы хотите писать меньше кода - Вам важна
долгосрочная стабильность

*Когда оставаться на TypeScript:* - Вам нужна работа (больше вакансий) -
Команда не готова к новому языку - Проект требует максимального быстрого
старта

*Реальность:* Можно знать оба. TypeScript для работы, CLJS для души и
side projects. Концепции из CLJS сделают вас лучшим TypeScript
разработчиком.

*** Работает ли WebAssembly с ClojureScript?
:PROPERTIES:
:CUSTOM_ID: работает-ли-webassembly-с-clojurescript
:END:
*Да, но это не основной use case.*

*Варианты:*

*1. Вызов WASM из CLJS*

#+begin_src clojure
(defn use-wasm []
  (-> (js/WebAssembly.instantiate module)
      (.then (fn [instance]
               (let [exports (.-exports instance)]
                 (.add exports 1 2))))))
#+end_src

*2. Компиляция Clojure в WASM* - Экспериментальные проекты есть - Не
production-ready

*3. ClojureDart → Flutter (компилируется в native через Dart)*

*Когда нужно:* - Performance-critical вычисления (криптография, image
processing) - Интеграция с Rust/C++ библиотеками

*Реальность:* Большинство CLJS приложений не нуждаются в WASM. Если вам
критична производительность: 1. Используйте transducers 2. Оптимизируйте
алгоритмы 3. Вынесите тяжёлые вычисления на backend 4. Web Workers для
параллельности

WASM используйте только если действительно нужна near-native performance
в браузере.

*** Есть ли CI/CD примеры для ClojureScript?
:PROPERTIES:
:CUSTOM_ID: есть-ли-cicd-примеры-для-clojurescript
:END:
*Да, shadow-cljs легко интегрируется.*

*GitHub Actions:*

#+begin_src yaml
name: Build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - uses: actions/setup-java@v2
        with:
          java-version: '17'
      - uses: actions/setup-node@v2
      - run: npm install
      - run: npx shadow-cljs release app
      - run: npx shadow-cljs compile test
#+end_src

*GitLab CI:*

#+begin_src yaml
build:
  image: clojure:openjdk-17
  script:
    - npm install
    - npx shadow-cljs release app
  artifacts:
    paths:
      - public/js/
#+end_src

*Docker:*

#+begin_src dockerfile
FROM clojure:openjdk-17
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm install
COPY . .
RUN npx shadow-cljs release app
#+end_src

*Что нужно:* - Java 11+ (для shadow-cljs) - Node.js (для npm
dependencies) - ~5-10 минут для production build

*Caching:*

#+begin_src yaml
- uses: actions/cache@v2
  with:
    path: |
      ~/.m2
      node_modules
    key: ${{ runner.os }}-deps-${{ hashFiles('**/deps.edn', '**/package-lock.json') }}
#+end_src

Это ускоряет билды до 1-2 минут.
