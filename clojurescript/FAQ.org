*** Зачем столько скобок?
:PROPERTIES:
:CUSTOM_ID: зачем-столько-скобок
:END:
Скобки в [[https://clojurescript.org][ClojureScript]] — фундаментальная особенность, а не недостаток. [[https://spin.atomicobject.com/2013/07/23/homoiconicity-clojure-macros/][Homoiconicity]] превращает код в данные, позволяя [[https://clojure.org/reference/macros][макросам]] генерировать код во время компиляции. Правильные редакторы с [[https://paredit.org/][paredit]]/[[https://shaunlebron.github.io/parinfer/][parinfer]] делают скобки невидимыми, устраняя необходимость запоминать различия между `{}`, `[]`, `()` как в императивных языках.

Современные инструменты — [[https://betterthantomorrow.github.io/calva/][VSCode с Calva]], [[https://cursive-ide.com/][IntelliJ с Cursive]], [[https://cider.mx/][Emacs с CIDER]] — автоматически управляют структурой кода, превращая кажущуюся сложность в преимущество единообразия.

*** Есть ли аналог TypeScript для ClojureScript?
:PROPERTIES:
:CUSTOM_ID: есть-ли-аналог-typescript-для-clojurescript
:END:
ClojureScript не нуждается в TypeScript по фундаментальным причинам:

*Runtime validation* — [[https://clojure.org/guides/spec][clojure.spec]] и [[https://github.com/metosin/malli][malli]] обеспечивают валидацию данных во время выполнения, охватывая входы/выходы функций, API и состояние приложения. 

*Immutable data structures* — [[https://clojure.org/reference/data_structures][неизменяемость структур]] устраняет целые классы ошибок, которые TypeScript лишь пытается предотвратить в императивных языках.

*[[https://clojure.org/reference/repl_and_main][REPL-driven development]]* позволяет тестировать функции с реальными данными непосредственно при написании, выявляя ошибки раньше статической типизации.

Для статической типизации существуют экспериментальные [[https://github.com/clojure/core.typed][typed-clojure]] проекты, но большинство разработчиков предпочитают комбинацию spec + REPL.

*** Сколько времени занимает изучение ClojureScript?
:PROPERTIES:
:CUSTOM_ID: сколько-времени-занимает-изучение-clojurescript
:END:
*Базовый синтаксис*: 1-2 недели для чтения и понимания кода.

*Написание простых приложений*: 2-3 месяца для уверенной работы с [[https://reagent-project.github.io/][Reagent]]/[[https://day8.github.io/re-frame/][re-frame]].

*Продуктивная работа*: 3-6 месяцев для комфортного написания production кода.

Основная сложность не в синтаксисе (его очень мало), а в необходимости "разучиться" думать императивно и объектно-ориентированно. Функциональное программирование требует иного подхода к решению задач.

Большинство проблем новичков связаны не с функциональной парадигмой, а с незнанием [[https://clojure.github.io/clojure/clojure.core-api.html][clojure.core]] API и платформенных особенностей ([[https://clojure.org/][JVM]] для Clojure, JavaScript для ClojureScript).

*** Как дебажить ClojureScript?
:PROPERTIES:
:CUSTOM_ID: как-дебажить-clojurescript
:END:
*Browser DevTools*

#+begin_src clojure
(js/console.log "debug:" value)
(js/console.table data)
#+end_src

*REPL debugging* — самый мощный способ: оценивать выражения прямо в REPL:

#+begin_src clojure
(def state (atom {:users []}))
@state  ; посмотреть текущее состояние
(swap! state assoc :debug true)  ; изменить на лету
#+end_src

*tap>* — современный способ дебага:

#+begin_src clojure
(tap> {:event :user-clicked :data user})
#+end_src
Данные попадают в tap-системы ([[https://github.com/djblue/portal][Portal]], [[https://github.com/vlaaad/reveal][Reveal]])

*[[https://github.com/Day8/re-frame-10x][re-frame-10x]]* (для re-frame приложений) — Time-travel debugging, просмотр всех events/effects, diff состояний.

*Source maps* — [[https://shadow-cljs.github.io/docs/UsersGuide.html][Shadow-cljs]] автоматически генерирует source maps, поэтому в Chrome DevTools вы видите оригинальный CLJS код, а не скомпилированный JS.

*** Можно ли использовать npm библиотеки?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-npm-библиотеки
:END:
Да, [[https://shadow-cljs.github.io/docs/UsersGuide.html][shadow-cljs]] имеет first-class поддержку npm:

#+begin_src clojure
;; package.json
{
  "dependencies": {
    "react": "^18.0.0",
    "lodash": "^4.17.21"
  }
}

;; ClojureScript
(ns app.core
  (:require ["react" :as react]
            ["lodash" :as _]))

(react/createElement "div" nil "Hello")
(_.debounce my-fn 300)
#+end_src

*Interop с React компонентами:*

#+begin_src clojure
(:require ["@mui/material" :refer [Button TextField]])

(defn my-component []
  [:> Button {:variant "contained"
              :on-click #(js/alert "Clicked")}
   "Click me"])
#+end_src

Работают все npm библиотеки без исключений. Для React-компонентов есть удобный синтаксис *[:> Component props]*.

** Производительность
:PROPERTIES:
:CUSTOM_ID: производительность
:END:
*** Persistent data structures медленные?
:PROPERTIES:
:CUSTOM_ID: persistent-data-structures-медленные
:END:
*Короткий ответ*: Нет, для большинства приложений они быстрее.

*Технически*: [[https://clojure.org/reference/data_structures][Persistent structures]] используют [[https://hypirion.com/musings/understanding-persistent-vector-part-1][structural sharing]] — копируется только изменённая часть дерева (O(log32 N)). Сравнение коллекций — O(1) благодаря hash и reference equality. Не нужно делать defensive копии как в JS (*{...obj}*).

*React/Reagent context*: В React нужно *memo()*, *useMemo()*, *useCallback()* для оптимизации. В [[https://reagent-project.github.io/][Reagent]] structural sharing + *identical?* проверка дают автоматическую оптимизацию без memo. shouldComponentUpdate бесплатно благодаря [[https://clojure.org/reference/data_structures#Immutability][immutability]].

*Производительность*: зависит от конкретного случая использования. Persistent data structures используют структурное разделение (structural sharing), что позволяет избежать копирования целых коллекций при изменениях. В React нужно использовать *memo()*, *useMemo()*, *useCallback()* для оптимизации, в то время как в Reagent за счет immutability оптимизация работает автоматически.

Если нужна максимальная производительность, есть [[https://clojure.org/reference/transients][transients]] для batch mutations: O(1) как у мутабельных структур, но с гарантиями immutability после завершения.

*** Какой bundle size у ClojureScript приложений?
:PROPERTIES:
:CUSTOM_ID: какой-bundle-size-у-clojurescript-приложений
:END:
*Реальные цифры:*

Hello World с [[https://reagent-project.github.io/][Reagent]]: ~200-250 KB (gzip) —
- React: ~42 KB,
- ClojureScript runtime: ~70 KB,
- Reagent: ~15 KB,
- Google Closure runtime: ~90 KB.

Среднее production приложение: 500 KB - 1 MB (gzip).

*Важно понимать*: первоначальный bundle больше чем у Vue/React, но рост замедляется благодаря отсутствию дублирования кода при добавлении новой функциональности. [[https://developers.google.com/closure/compiler][Google Closure Compiler]] удаляет мёртвый код агрессивнее чем Webpack/Rollup. Code splitting работает из коробки. Для landing pages не лучший выбор, для продуктивных SPA приложений разница между 500 KB и 1 MB не критична.

*Оптимизации:*

#+begin_src clojure
;; shadow-cljs.edn
:compiler-options {:infer-externs :auto}  ; автоматический advanced compilation
:module-hash-names true  ; для кеширования
#+end_src

*** Hot reload работает нормально?
:PROPERTIES:
:CUSTOM_ID: hot-reload-работает-нормально
:END:
*Да, и это одна из killer features ClojureScript.*

[[https://shadow-cljs.github.io/docs/UsersGuide.html][Shadow-cljs]] поддерживает hot reload без потери state:

#+begin_src clojure
(defonce state (atom {:count 0}))  ; defonce сохраняет state при reload

(defn component []
  [:div @state])  ; изменения компонента применяются мгновенно
#+end_src

*Почему это работает лучше чем в React*: функции без побочных эффектов можно перезагружать безопасно. State в atoms/[[https://day8.github.io/re-frame/][re-frame]] живёт независимо от компонентов. Нет lifecycle hooks, которые нужно пересоздавать.

*Fast Refresh в React vs CLJS*: React Fast Refresh требует специальных правил (hooks должны быть в правильном порядке, etc). CLJS hot reload просто работает для любых функций.

Время от сохранения файла до обновления в браузере: обычно < 1 секунды.

*** Startup time какой?
:PROPERTIES:
:CUSTOM_ID: startup-time-какой
:END:
*Development*: первая компиляция (cold start): 10-30 секунд в зависимости от размера проекта. Incremental компиляция: 0.5-2 секунды. REPL startup: 5-10 секунд.

*Production build*:
- small app: 30-60 секунд.
- large app: 2-5 минут.

[[https://developers.google.com/closure/compiler][Google Closure advanced compilation]] медленная, но результат того стоит.

*Runtime (в браузере)*: инициализация CLJS runtime: минимальная, незаметная. Первый рендер: сравнимо с React.

*Сравнение с TypeScript/Vite*: development: CLJS медленнее на первом запуске, но incremental compile сравним. Production: CLJS медленнее (из-за Closure Compiler), но bundle меньше и оптимизированнее.

Для больших команд обычно используют CI для production builds, dev builds достаточно быстрые.

*** Есть ли поддержка SSR/SEO?
:PROPERTIES:
:CUSTOM_ID: есть-ли-поддержка-ssrseo
:END:
*Да, но это не основной use case.*

*Для SEO есть несколько подходов:*

1. *Pre-rendering* (рекомендуется) — используйте [[https://prerender.io/][prerender.io]] или headless Chrome для генерации статики. Подходит для большинства случаев.

2. *Server-Side Rendering* — библиотеки: reagent-server (experimental). Node.js: можно рендерить CLJS на Node через [[https://shadow-cljs.github.io/][shadow-cljs]]. JVM: можно использовать [[https://clojure.org/][Clojure]] на бэкенде для server-side rendering.

3. *Static Site Generation* — для блогов/документации: [[https://github.com/cryogen-project/cryogen][Cryogen]] (Clojure SSG).

*Реальность*: большинство CLJS приложений — это productivity apps (admin панели, dashboards, internal tools), где SEO не критично. Для marketing сайтов обычно используют отдельный стек (Next.js, Astro).

Если SEO критично для всего приложения — возможно, CLJS не лучший выбор.

*** Как тестировать ClojureScript код?
:PROPERTIES:
:CUSTOM_ID: как-тестировать-clojurescript-код
:END:
*Unit тесты:*

#+begin_src clojure
(ns app.core-test
  (:require [cljs.test :refer [deftest is testing]]))

(deftest addition-test
  (is (= 4 (+ 2 2))))
#+end_src

*Запуск:*

#+begin_src sh
npx shadow-cljs compile test
# или с watch
npx shadow-cljs watch test
#+end_src

*Популярные библиотеки*: [[https://clojure.github.io/clojurescript/clojure.test-api.html][cljs.test]] (встроенная), [[https://github.com/clojure/test.check][clojure.test.check]] (property-based testing), [[https://github.com/day8/re-frame-test][day8/re-frame-test]] для re-frame приложений.

*E2E тесты*: [[https://www.cypress.io/][Cypress]] работает как с обычным SPA, [[https://playwright.dev/][Playwright]] тоже работает.

*REPL-based testing*: многие разработчики тестируют функции прямо в REPL:

#+begin_src clojure
(defn process-data [data]
  (tap> {:input data})  ; debug
  (->> data
       (filter valid?)
       (map transform)))

;; В REPL:
(process-data test-data)  ; сразу видим результат
#+end_src

*Факты*: [[https://clojure.org/][Clojure]] был релизнут в 2007 году (18 лет). ClojureScript — 2011 год (14 лет). Clojure 1.12.0 вышел в сентябре 2024 (активная разработка). 58% респондентов State of Clojure 2024 уже используют новейшую версию.

*Стабильность*: backwards compatibility — приоритет. Код 10-летней давности работает без изменений. Нет breaking changes каждый год как в JS экосистеме.

*Корпоративная поддержка*: [[https://nubank.com.br/][Nubank]] (700+ разработчиков) — не умрёт завтра. [[https://cognitect.com/][Cognitect]] (создатели Clojure) — продолжают развитие. Datomic, Babashka — активные проекты экосистемы.

*Adoption*: не растёт взрывными темпами как JS frameworks. Стабильная ниша: fintech, enterprise, data engineering. Рост в больших компаниях (100-1000 сотрудников).

*Риски*: меньше новых разработчиков чем в JS/TS. Если ключевые люди уйдут — возможно замедление развития. JVM dependency (но это и преимущество).

*Реальность*: Clojure — это не модный фреймворк, который умрёт через 5 лет. Это mature технология с stable core и долгосрочной перспективой. Если вы учите CLJS сейчас, он будет актуален минимум ещё 10+ лет.

Сравните с JS: сколько фреймворков умерло за 10 лет? Angular.js, Backbone, Ember (почти), сейчас под вопросом даже React. Clojure — стабильность.

*** Сложно ли нанять Clojure разработчиков?
:PROPERTIES:
:CUSTOM_ID: сложно-ли-нанять-clojure-разработчиков

*Да, сложнее чем React/Vue разработчиков.*

*Почему сложно*: меньше специалистов на рынке. Большинство уже трудоустроены (73% используют на работе). Конкуренция за Clojure разработчиков высокая. В СНГ практически нет рынка.

*Стратегии*:

1. *Train, don't hire* — нанимайте strong разработчиков и обучайте Clojure. [[https://nubank.com.br/][Nubank]] использует такой подход. Timeline: 3-6 месяцев до продуктивности.

2. *Remote-first* — большинство Clojure вакансий — remote. Расширяет географию поиска.

3. *Community engagement* — активность в [[https://clojurians.slack.com/][Clojurians Slack]], спонсирование конференций ([[https://clojure-conj.org/][Clojure/conj]]), open source проекты.

4. *Strong компенсация* — зарплаты выше среднего, интересные технические задачи.

*Альтернативный подход*: не переводите всё на Clojure. Используйте его для backend API (где можно нанять JVM разработчиков и обучить Clojure), internal tools, data processing.

Frontend оставьте на React/Vue/TS (больше кандидатов).

*** Сколько времени занимает онбординг разработчика?
:PROPERTIES:
:CUSTOM_ID: сколько-времени-занимает-онбординг-разработчика
:END:
*Зависит от бэкграунда:*

*JavaScript/TypeScript разработчик без FP опыта*: чтение кода: 3-4 недели. Простые задачи: 1.5-2.5 месяца. Полная продуктивность: 5-7 месяцев.

*Java/Backend разработчик*: Clojure (backend) осваивают быстрее: 1-3 месяца. ClojureScript: +2 месяца (нужно понять React/frontend).

*Функциональный бэкграунд (Haskell, Scala, F#)*: syntax: 1-2 недели. Продуктивность: 1-2 месяца.

*Что помогает онбордингу*:

1. *Парное программирование* — код ревью с объяснениями, mob programming сессии.

2. *Структура кодбейзы* — чёткие naming conventions, документированные архитектурные решения.

3. *[[https://clojure.org/reference/repl_and_main][REPL-driven development]]* — быстрая обратная связь, экспериментирование без последствий.

4. *Ресурсы*: "[[https://www.braveclojure.com/][Clojure for the Brave and True]]" (книга), [[https://clojurescript.org/guides/quick-start][ClojureScript Quick Start]], внутренние гайды компании.

*State of Clojure 2024*: большинство разработчиков пришли из Java, JavaScript, Python — все успешно освоили язык.

*** Можно ли использовать ClojureScript в команде из одного человека?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-clojurescript-в-команде-из-одного-человека
:END:
*Да, и это даже лучше чем в большой команде.*

*Почему solo dev выигрывает*:

1. *Нет онбординга* — не нужно обучать команду, пишете как удобно вам.

2. *Fullstack из коробки* — один язык для frontend/backend, shared code (.cljc), меньше context switching.

3. *Долгосрочная стабильность* — код не устаревает как JS frameworks, меньше рефакторингов из-за breaking changes.

4. *Производительность* — [[https://clojure.org/reference/repl_and_main][REPL-driven development]] быстрее, меньше boilerplate, меньше времени на настройку tooling.

*Когда не стоит*: планируете быстро масштабировать команду, нужно продать продукт (а не technology), критично время до маркета (time to market).

*Реальные кейсы*: многие solo developers используют Clojure/CLJS для SaaS продуктов, internal tools, data analysis tools, MVPs.

*Recommendation*: если вы solo и не планируете быстро расти — CLJS отличный выбор. Если нужна команда через полгода — возможно, React/TS безопаснее.

** Интероп и миграция
:PROPERTIES:
:CUSTOM_ID: интероп-и-миграция
:END:
*** Можно ли использовать любую React библиотеку в ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-любую-react-библиотеку-в-clojurescript
:END:
*Да, любую.*

*Синтаксис:*

#+begin_src clojure
;; npm install @mui/material
(:require ["@mui/material" :refer [Button TextField Dialog]])

(defn my-form []
  [:div
   [:> TextField {:label "Name"
                  :value @name
                  :on-change #(reset! name (.. % -target -value))}]
   [:> Button {:variant "contained"
               :on-click handle-submit}
    "Submit"]])
#+end_src

*`:>` — специальный синтаксис [[https://reagent-project.github.io/][Reagent]] для React компонентов.*

*Hooks (experimental):*

#+begin_src clojure
(:require ["react" :as react])
;; Примечание: в Reagent обычно не требуется прямой импорт React

(defn use-fetch [url]
  (let [[data set-data] (react/useState nil)]
    (react/useEffect
      (fn []
        (-> (js/fetch url)
            (.then #(.json %))
            (.then #(set-data %))))
      #js [url])
    data))
#+end_src

*TypeScript типы*: теряются, нужно смотреть в документацию библиотеки.

*Что работает*: [[https://mui.com/][Material-UI]], [[https://ant.design/][Ant Design]], [[https://chakra-ui.com/][Chakra UI]], [[https://www.react-spring.dev/][React Spring]], [[https://www.framer.com/motion/][Framer Motion]] (анимации), [[https://react-query.tanstack.com/][React Query]], [[https://swr.vercel.app/][SWR]] (data fetching), [[https://recharts.org/][Recharts]], [[https://github.com/FormidableLabs/victory][Victory]] (графики), [[https://reactrouter.com/][React Router]] (хотя есть [[https://github.com/metosin/reitit-frontend][reitit-frontend]]).

*Что может быть сложно*: библиотеки с complex TypeScript types, генераторы кода (нужны workarounds), компоненты с императивным API (ref based).

*** Можно ли использовать Vue компоненты в ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-использовать-vue-компоненты-в-clojurescript
:END:
*Технически возможно, но не рекомендуется.*

ClojureScript обычно использует React (через [[https://reagent-project.github.io/][Reagent]]), а не Vue. Интеграция Vue компонентов потребует: подключить Vue runtime, создать мост между Vue и React/Reagent, разбираться с двумя реактивными системами.

*Альтернативы*: используйте React версию компонента (большинство UI библиотек есть для обоих), перепишите компонент на Reagent (часто проще чем кажется), оставьте часть приложения на Vue, часть на CLJS (микрофронтенды).

*Реальность*: если вы хотите использовать Vue компоненты — возможно, стоит остаться на Vue вместо миграции на CLJS.

*** Можно ли постепенно мигрировать проект на ClojureScript?
:PROPERTIES:
:CUSTOM_ID: можно-ли-постепенно-мигрировать-проект-на-clojurescript
:END:
*Да, несколько стратегий:*

*1. Новые фичи на CLJS* — существующий код остаётся на React/Vue, новые компоненты пишете на [[https://reagent-project.github.io/][Reagent]], общаются через props/events.

*2. По страницам* — главная страница React, admin панель ClojureScript, общий state через localStorage или API.

*3. Backend первым* — переписываете API на [[https://clojure.org/][Clojure]], frontend остаётся React/Vue, постепенно shared код переносите в .cljc.

*4. Micro-frontends* — разные части приложения разные технологии, изоляция через iframe или Web Components.

*Реальность*: большинство компаний НЕ мигрируют существующие проекты на CLJS. Вместо этого новые проекты начинают на CLJS, legacy остаётся на старом стеке, или ре-write при мажорном редизайне.

*Если планируете миграцию*: начните с backend (Clojure легче продать чем ClojureScript), доказывайте ценность на production, только потом переходите к frontend.

*** Нужно ли переписывать backend на Clojure если используете ClojureScript?
:PROPERTIES:
:CUSTOM_ID: нужно-ли-переписывать-backend-на-clojure-если-используете-clojurescript
:END:
*Нет, не обязательно.*

*Варианты*:

*1. CLJS frontend + Node.js/Python/Java backend* — работает нормально, теряете .cljc shared code, дублируете validation/models.

*2. CLJS frontend + [[https://clojure.org/][Clojure]] backend* — идеальный вариант, shared код (.cljc), одна команда, один язык.

*3. CLJS frontend + любой REST/GraphQL API* — backend может быть на чём угодно, CLJS просто делает HTTP запросы.

*Когда имеет смысл Clojure backend*: пишете новый проект с нуля, backend логика сложная (fintech, data processing), хотите fullstack команду.

*Когда НЕ имеет смысл*: backend работает отлично и менять незачем, команда backend не хочет учить Clojure, backend на другом языке и переписывать дорого.

*Преимущества CLJS даже без Clojure backend*: [[https://clojure.org/reference/data_structures#Immutability][immutability]], [[https://clojure.org/reference/repl_and_main][REPL-driven development]], [[https://day8.github.io/re-frame/][re-frame]] для state management, [[https://hypirion.com/musings/understanding-persistent-vector-part-1][structural sharing]] для performance.

Вы всё равно получаете большую часть выгоды от CLJS.

** Дополнительные вопросы
:PROPERTIES:
:CUSTOM_ID: дополнительные-вопросы
:END:
*** Зачем учить новый синтаксис если есть TypeScript?
:PROPERTIES:
:CUSTOM_ID: зачем-учить-новый-синтаксис-если-есть-typescript
:END:
*Философский ответ*: TypeScript решает проблемы JavaScript, добавляя типы. ClojureScript решает фундаментальные проблемы программирования: [[https://clojure.org/reference/data_structures#Immutability][immutability]], simplicity, data-oriented design.

*Практический ответ*:

*TypeScript даёт*: compile-time type safety, better IDE autocomplete, refactoring tools.

*ClojureScript даёт*: runtime type safety ([[https://clojure.org/guides/spec][spec]]/[[https://github.com/metosin/malli][malli]]), immutability из коробки, [[https://clojure.org/reference/repl_and_main][REPL-driven development]], меньше кода (threading macros, destructuring), stable platform (код 10-летней давности работает), [[https://spin.atomicobject.com/2013/07/23/homoiconicity-clojure-macros/][homoiconicity]] (код = данные, макросы).

*Когда учить CLJS*: вам интересен функциональный подход, вы устали от JavaScript fatigue, вы хотите писать меньше кода, вам важна долгосрочная стабильность.

*Когда оставаться на TypeScript*: вам нужна работа (больше вакансий), команда не готова к новому языку, проект требует максимального быстрого старта.

*Реальность*: можно знать оба. TypeScript для работы, CLJS для души и side projects. REPL-driven development предоставляет мгновенную обратную связь, что ускоряет разработку. Концепции из CLJS сделают вас лучшим TypeScript разработчиком.

*** Работает ли WebAssembly с ClojureScript?
:PROPERTIES:
:CUSTOM_ID: работает-ли-webassembly-с-clojurescript
:END:
*Да, но это не основной use case.*

*Варианты*:

*1. Вызов WASM из CLJS*

#+begin_src clojure
(defn use-wasm []
  (-> (js/WebAssembly.instantiate module)
      (.then (fn [instance]
               (let [exports (.-exports instance)]
                 (.add exports 1 2))))))
#+end_src

*2. Компиляция Clojure в WASM* — экспериментальные проекты есть, не production-ready.

*3. [[https://github.com/tatut/clojureskript][ClojureDart]] → Flutter (компилируется в native через Dart).

*Когда нужно*: performance-critical вычисления (криптография, image processing), интеграция с Rust/C++ библиотеками.

*Реальность*: большинство CLJS приложений не нуждаются в WASM. Если вам критична производительность: используйте [[https://clojure.org/reference/transducers][transducers]], оптимизируйте алгоритмы, вынесите тяжёлые вычисления на backend, Web Workers для параллельности.

WASM используйте только если действительно нужна near-native performance в браузере.

*** Есть ли CI/CD примеры для ClojureScript?
:PROPERTIES:
:CUSTOM_ID: есть-ли-cicd-примеры-для-clojurescript
:END:
*Да, shadow-cljs легко интегрируется.*

*GitHub Actions:*

#+begin_src yaml
name: Build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v2
        with:
          java-version: '17'
      - uses: actions/setup-node@v2
      - run: npm install
      - run: npx shadow-cljs release app
      - run: npx shadow-cljs compile test
#+end_src

*GitLab CI:*

#+begin_src yaml
build:
  image: clojure:openjdk-17
  script:
    - npm install
    - npx shadow-cljs release app
  artifacts:
    paths:
      - public/js/
#+end_src

*Docker:*

#+begin_src dockerfile
FROM clojure:openjdk-17
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm install
COPY . .
RUN npx shadow-cljs release app
#+end_src

*Что нужно:* - Java 11+ (для shadow-cljs) - Node.js (для npm
dependencies) - ~5-10 минут для production build

*Caching:*

#+begin_src yaml
- uses: actions/cache@v2
  with:
    path: |
      ~/.m2
      node_modules
    key: ${{ runner.os }}-deps-${{ hashFiles('**/deps.edn', '**/package-lock.json') }}
#+end_src

Это значительно ускоряет билды.
