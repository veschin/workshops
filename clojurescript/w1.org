** Гомоиконность: Код как данные

Гомоиконность стирает грань между кодом и данными — оба становятся коллекциями. В JavaScript/TS код остаётся текстом (строки), данные — объектами/массивами. ClojureScript унифицирует всё в неизменяемые структуры, превращая манипуляции кодом в операции с данными [[https://spin.atomicobject.com/2013/07/23/homoiconicity-clojure-macros/][Lisps are homoiconic: code encoded as data structures]].

*** Базовые структуры в CLJS и аналогии в JS/TS

CLJS опирается на четыре immutable коллекции с structural sharing. Они служат основой для данных, UI и кода [[https://clojure.org/reference/data_structures][All Clojure collections are immutable and persistent]].

| Структура CLJS | Описание                                    | Аналог в JS/TS                   | Разница                                                                                      |
| Vector `[]`    | Упорядоченный список с доступом по индексу. | Array `[]`                       | CLJS: Persistent (assoc создаёт копию efficiently); JS: Изменяемая (push мутирует).          |
| Map `{}`       | Ключ-значение (ключи — keywords).           | Object `{}` или Map              | CLJS: Keywords как функции (`(:name obj)`); JS: Строки/символы, без функциональности ключей. |
| List `()`      | Последовательность (для кода).              | Нет нативного (LinkedList в lib) | CLJS: Для S-выражений (код); JS: Код — строки.                                               |
| Set `#{}`      | Уникальные значения.                        | Set                              | CLJS: Persistent (неизменяемая); JS: Изменяемая.                                             |

Пример данных:
#+begin_src clojure
;; CLJS: Коллекции
(def data [1 2 3])  ; vector
(def obj {:name "John" :age 30})  ; map
(:name obj)  ; => "John" (keyword как функция)
#+end_src

#+begin_src javascript
// JS: Разные типы
const data = [1, 2, 3];  // array
const obj = {name: "John", age: 30};  // object
obj.name;  // "John" (точечный доступ)
#+end_src

В CLJS функции `map/filter/get-in` работают uniformно. В JS — разные API.

*** Код как коллекции

В CLJS код — не текст, а коллекции. Цитирование (quote) позволяет манипулировать, eval — выполнять.

#+begin_src clojure
;; Данные
[1 2 3]
{:name "John"}

;; Код как коллекции
'(+ 1 2 3)  ; list (quote не eval'ит)
(eval '(+ 1 2 3))  ; => 6

;; Манипуляция
(def code '(+ 1 2))
(conj code 3)  ; => (+ 1 2 3)
(eval (conj code 3))  ; => 6
#+end_src

#+begin_src javascript
// JS: Код как текст (AST через Babel — не нативно)
const codeStr = "(a, b) => a + b";  // строка
const ast = babel.parse(codeStr);  // парсинг в объект
ast.program.body[0].expression.params.push({type: 'Identifier', name: 'c'});  // сложная манипуляция
const newCode = babel.generate(ast).code;  // "(a, b, c) => a + b"
eval(newCode);  // выполнение (рискованно)
#+end_src

В JS манипуляция требует внешних инструментов. В CLJS — нативно, безопасно в REPL.

*** Data-driven UI: Применение для фронтенда

Гомоиконность позволяет генерировать UI из данных, трансформировать как коллекции. Нет разделения template/logic.

**** Hiccup: UI как вектор (vs JSX)

#+begin_src clojure
;; Hiccup — вектор
[:div {:class "container"} [:h1 "Title"] [:p "Content"]]

;; Трансформация данных
(defn add-class [hiccup cls]
  (if (= :div (first hiccup)) (update hiccup 1 assoc :class cls) hiccup))

(add-class [:div "Hello"] "highlight")  ; => [:div {:class "highlight"} "Hello"]
#+end_src

#+begin_src javascript
// JSX — сахар (компиляция в createElement)
const element = <div className="container"><h1>Title</h1></div>;  // не данные

// Data-driven в JS: Объекты + manual render
const uiObj = {type: 'div', props: {className: 'container'}, children: [{type: 'h1', children: 'Title'}]};
function transform(ui) { if (ui.type === 'div') ui.props.className += ' highlight'; return React.createElement(ui.type, ui.props, ui.children); }  ; verbose, mutable
#+end_src

**** Динамическая генерация UI

#+begin_src clojure
(def menu [{:label "Home" :url "/"} {:label "About" :url "/about"}])

(defn nav [] [:nav (for [item menu] [:a {:href (:url item)} (:label item)])])
; => [:nav [:a {:href "/"} "Home"] ...] — map/for на данных
#+end_src

#+begin_src javascript
// JS: Map к JSX, но объекты mutable
const menu = [{label: 'Home', url: '/'} , {label: 'About', url: '/about'}];
const nav = <nav>{menu.map(item => <a href={item.url}>{item.label}</a>)}</nav>;  ; compile-time, no transform как данные
#+end_src

**** Макросы: Генерация кода из данных

#+begin_src clojure
(defmacro when-let [binding & body]
  `(let [val# ~(second binding)]  ; ~ вставляет данные
     (when val# (let [~(first binding) val#] ~@body))))  ; код как коллекции

(when-let [user (get-user)] (greet user))  ; генерирует let/when без boilerplate
#+end_src

#+begin_src javascript
// JS: Нет native; Babel plugin для gen (compile-time)
const whenLetCode = `if (user) { greet(user); }`;  ; строки, no REPL-manip
#+end_src

| Разделение template/logic (Vue) | UI=функции данных: (defn comp [data] [:div data.name]). |
| Code gen (Babel)                | Макросы/eval: REPL манипулирует кодом live.             |

*** Демо: Data-driven UI из API

#+begin_src clojure
(def api {:type :form :fields [{:type :text :label "Name"} {:type :submit :label "Send"}]})

(defn render-field [f] (case (:type f) :text [:input {:placeholder (:label f)}] :submit [:button (:label f)]))

(render-form api)  ; map/case на данных → Hiccup
; => [:form [:input {:placeholder "Name"}] [:button "Send"]]
#+end_src

#+begin_src javascript
// JS: Switch на объектах + manual render
const api = {type: 'form', fields: [{type: 'text', label: 'Name'}, {type: 'submit', label: 'Send'}]};
function renderField(f) { switch (f.type) { case 'text': return <input placeholder={f.label} />; case 'submit': return <button>{f.label}</button>; } }
const form = <form>{api.fields.map(renderField)}</form>;  ; verbose, no uniform transform
#+end_src

В React/Vue: if/switch + registry — многословно.

*** Ключевой инсайт

В JavaScript: Код=текст (парсинг в AST), данные=объекты (mutable, разные ops), UI=JSX (компиляция). Data-driven — manual (lodash).  
В ClojureScript: Всё=коллекции (immutable, uniform). Data-driven нативно: UI/код трансформируются как данные, REPL eval'ит всё. Для фронтенда: Генерация UI из API тривиальна, без boilerplate.

** Структуры данных: Основа для UI и управления состоянием
Структуры данных в CLJS — это persistent коллекции с нативной поддержкой путей. Они решают ключевые проблемы React/Vue: обновление вложенного состояния и предсказуемая реактивность через structural sharing [[https://clojure.org/reference/data_structures][Clojure collections support efficient 'modified' versions via structural sharing]].

*** Почему векторы подходят для создания UI в Hiccup?
Векторы — это упорядоченные списки, удобные для вложенных структур. В Hiccup вектор описывает элемент: первый элемент — тег, второй (если есть) — атрибуты (как словарь), остальное — дочерние элементы. Это позволяет манипулировать UI как обычными данными.

#+begin_src clojure
;; Простой UI как обычные данные
[:div {:class "container"}
  [:h1 "Заголовок"]
  [:ul
    (for [item items] [:li (:name item)])]]  ; рендер на основе данных

;; Изменение: добавляем класс ко всем div (создаёт новую копию, оригинал не меняется)
(update-in ui [0 1 :class] #(str % " highlight"))  ; всего одна строка
#+end_src

#+begin_src javascript
;; В React/JSX: spread создаёт shallow копию, для вложенных нужно повторять (официально: "use it more than once for nested")
const ui = {type: 'div', props: {className: 'container'}, children: [{type: 'h1', children: 'Заголовок'}]};
const updated = {...ui, props: {...ui.props, className: ui.props.className + ' highlight'}};  ; verbose для nested
#+end_src

**** Сравнение Hiccup и JSX
| Аспект          | Hiccup (CLJS)                          | JSX (React/Vue)                  |
|-----------------|----------------------------------------|----------------------------------|
| Формат          | Обычные векторы (как данные)           | Специальный синтаксис (нужна компиляция) |
| Изменения       | Унифицированные операции (assoc-in/update) | Копирование вручную (spread, легко ошибиться в nested) |
| Работа с вложенностью | Встроенная (get-in/assoc-in по путям) | Библиотеки вроде lodash (дополнительно) |
| Скорость        | Структурное разделение (эффективные копии) | Нужно вручную оптимизировать (memo) |

*** Вложенность и неизменяемость: Как упростить работу с глубоким состоянием
Коллекции CLJS созданы для глубоких структур — в них встроена работа с путями, и данные нельзя случайно изменить. В React spread для nested требует цепочки копий [[https://react.dev/learn/updating-objects-in-state][State can hold any kind of JavaScript value, but you shouldn't change objects directly]]; в Vue деструктуризация reactive объектов теряет реактивность (нужен toRefs) [[https://vuejs.org/guide/extras/reactivity-transform.html][It's easy to lose reactivity when destructuring reactive objects]].

#+begin_src clojure
(def state {:user {:profile {:address {:city "Москва" :settings {:theme "dark"}}}}})

;; Доступ и обновление по пути (решает проблему глубокого состояния)
(get-in state [:user :profile :address :city])  ; "Москва"
(update-in state [:user :profile :address :city] str/upper-case)  ; новая версия, оригинал остался прежним

;; Обновление состояния в UI
(defonce app-state (r/atom initial-state))
 (swap! app-state assoc-in [:user :profile :settings :theme] :dark)  ; реактивно, без устаревших значений
#+end_src

*** Всё неизменяемое (immutable)
В CLJS все коллекции неизменяемые: операции вроде assoc создают новую версию, оригинал остаётся нетронутым. Это предотвращает случайные мутации, которые часто вызывают баги в React/Vue.

#+begin_src clojure
(def data {:count 0})

;; Не изменяет оригинал
(assoc data :count 1)

data  ; => {:count 0}  (не изменился!)

;; Создаёт новую версию
(def updated (assoc data :count 1))
#+end_src

**** Релевантный пример: Обновление UI-state без мутации
Представьте счётчик в UI: в CLJS атом хранит immutable map, swap! создаёт новую версию — UI перерендерится только где нужно (благодаря structural sharing).

#+begin_src clojure
(defonce counter-atom (r/atom {:count 0 :label "Счётчик"}))

(defn counter-ui []
  [:div
   [:p "Значение: " (:count @counter-atom)]
   [:button {:on-click #(swap! counter-atom update :count inc)} "Увеличить"]])

;; Обновление: новая map, но старая часть shared (эффективно)
(swap! counter-atom assoc :label "Новый лейбл")  ; count не копируется заново
#+end_src

#+begin_src javascript
// В React: setState с объектом — легко мутировать случайно
const [state, setState] = useState({count: 0, label: 'Счётчик'});
const increment = () => setState({...state, count: state.count + 1});  // shallow copy, nested бы сломалось

// Ошибка: если забыть spread — мутация!
state.label = 'Мутация';  // Баг! State изменился глобально
#+end_src

Это делает state management предсказуемым: нет side-effects от мутаций, производительность выше за счёт sharing (только изменённые пути копируются).

#+begin_src javascript
;; В React: Цепочка spread для 5 уровней — 10+ строк, "React not oriented for nested states" [[https://stackoverflow.com/questions/43040721/how-to-update-nested-state-properties-in-react][The idea is to create a dummy object, perform operations, then replace state]]
const newState = {
  ...state,
  user: {
    ...state.user,
    profile: {
      ...state.user.profile,
      address: {
        ...state.user.profile.address,
        city: state.user.profile.address.city.toUpperCase()
      }
    }
  }
};  ; Легко пропустить — данные сломаются!

;; В Vue: Деструктуризация ломает reactive, "use toRefs to preserve reactivity" [[https://vuejs.org/guide/extras/reactivity-transform.html][It's easy to lose reactivity when destructuring reactive objects]]
const { city } = reactiveState.address;  // reactivity lost
#+end_src

*** Демо: Преобразование данных из API для UI
#+begin_src clojure
(def api-response
  [{:id 1 :name "john" :active true :tags ["vip" "new"]}
   {:id 2 :name "jane" :active false :tags ["vip"]}])

;; Цепочка операций: фильтр, преобразование, создание UI (threading, ключевые слова как функции)
(->> api-response
     (filter :active)
     (map (juxt :id (comp str/upper-case :name)))  ; [id имя-вверхнем-регистре]
     (mapcat (fn [[id name]] [[:tr {:key id}][:td name]]))  ; строки таблицы
     (into [:table]))  ; данные → готовый UI, всё унифицировано
;; => [:table [:tr {:key 1} [:td "JOHN"]]]  ; Hiccup готов к рендеру!
#+end_src

#+begin_src javascript
;; В JS: Цепочка работает, но с объектами (можно сломать), нет встроенных путей
apiResponse
  .filter(u => u.active)
  .map(u => ({id: u.id, name: u.name.toUpperCase()}))
  .map(({id, name}) => <tr key={id}><td>{name}</td></tr>);  // Смешано с JSX, преобразования не такие простые
#+end_src

*** Ключевой вывод для фронтенда
| Проблема в JS/TS + React/Vue | Решение в CLJS (неизменяемые структуры) |
|------------------------------|-----------------------------------------|
| Состояние меняется случайно → баги и тормоза | Неизменяемость: assoc-in создаёт дешёвую копию (structural sharing) |
| Сравнение глубоких данных дорогое | Сравнение по ссылке (быстрое) — рендер только где нужно |
| Нет простого доступа по путям | get-in/assoc-in: обновления вложенного в одну строку |
| Данные и UI разделены | Hiccup = данные: меняй как коллекции, тестируй в REPL |

Это упрощает управление состоянием (атомы + пути), сокращает лишний код на 50-70% и ускоряет разработку (не нужно следить за неизменяемостью вручную).

* Основные проблемы и решения
** Проблема 1: Обновление вложенного состояния
*** Проблема в React
- Spread operator hell
- Многословно и подвержено ошибкам
- Легко забыть про immutability

*** Проблема в Vue
- Реактивность ломается с динамическими свойствами
- Ограничения Proxy
- Путаница ref vs reactive

*** Решение в CLJS
- =assoc-in= / =update-in= / =get-in=
- Обновление по пути
- Всегда immutable, сломать нельзя

*** Демо
- Показать обновление состояния с 5 уровнями вложенности
- React: 15+ строк spread операторов
- Vue: footguns с реактивностью
- CLJS: 1 строка =assoc-in=

** Проблема 2: useEffect Dependency Hell
*** Проблема в React
- Stale closures из-за неправильных dependency array [[https://tkdodo.eu/blog/hooks-dependencies-and-stale-closures][Missing dependencies cause stale data from previous renders]]
- useCallback/useMemo повсюду для оптимизации [[https://imgeorgemor.medium.com/dont-get-fooled-by-usememo-and-usecallback-and-avoid-unnecessary-optimizations-2e7e854b487c][Most of the time you don't need any optimization built-in hook]]
- Бесконечные циклы при неправильных зависимостях

*** Проблема в Vue
- watch vs watchEffect vs computed путаница
- Ручное отслеживание зависимостей
- Сложная очистка

*** Решение в CLJS
- add-watch без closures [[https://clojure.org/reference/atoms][Atoms provide a mechanism for managing shared, synchronous, independent state]]
- Atoms реактивны по дизайну
- Нет массивов зависимостей
- Невозможны stale values

*** Демо
- WebSocket подключение с обновлением state
- Показать stale closure баг в React
- Показать простоту add-watch в CLJS

** Проблема 3: Vue3 Reactivity Footguns
*** Проблема в Vue
- Деструктуризация ломает реактивность
- Костыли с =toRefs=
- Путаница с ref.value
- Проблемы с динамическими свойствами

*** Решение в CLJS
- Неизменяемые данные
- Реактивность нельзя сломать
- Одна модель: atoms
- Консистентное поведение

*** Демо
- Деструктурировать Vue reactive объект → ломается
- То же в CLJS → работает, потому что immutable

** Проблема 4: Performance и Memo Hell
*** Проблема в React
- Ручной memo() везде [[https://react.dev/reference/react/memo][If there is no perceptible lag, memo is completely useless]]
- useMemo для каждого вычисления [[https://www.reddit.com/r/reactjs/comments/17yxuin/how_often_to_use_usecallbackusecallback/][Overuse of useCallback causes more performance problems than it saves]]
- Проверки reference equality вручную

*** Проблема в Vue
- computed vs methods непонятно
- Overhead реактивности
- Ручная оптимизация

*** Решение в CLJS
- Structural sharing [[https://clojure.org/reference/data_structures][Persistent data structures utilize structural sharing for efficiency]]
- identical? pointer comparison
- Автоматический shouldComponentUpdate
- Без ручной оптимизации

*** Демо
- Рендеринг большого списка
- React: нужен memo/useMemo
- CLJS: просто работает быстро

** Проблема 5: Runtime Validation
*** Проблема TypeScript
- Типы стираются при выполнении
- API возвращает неверную структуру → crash
- Нет runtime guards
- Нужны внешние библиотеки (Zod, io-ts) [[https://zod.dev/][TypeScript-first schema validation with static type inference]]

*** Решение в CLJS
- clojure.spec встроенный [[https://clojure.org/guides/spec][Spec library specifies the structure of data, validates or conforms it]]
- malli для продвинутых случаев [[https://github.com/metosin/malli][High-performance data-driven data specification library]]
- Runtime validation по умолчанию
- Детальные сообщения об ошибках

*** Демо
- TS interface проходит, runtime падает
- CLJS spec ловит на runtime

** Проблема 6: Shared Code (Frontend/Backend)
*** Проблема JS/TS
- Дублирование определения типов
- Сложность monorepo
- Ручная синхронизация моделей
- Проблемы с сериализацией

*** Решение в CLJS
- =.cljc= файлы
- Одна схема валидации
- Одна модель данных
- EDN сериализация

*** Демо
- Показать .cljc файл используемый и на фронте и на бэке
- Валидация работает с обеих сторон
- Нет дублирования

* Синтаксический сахар и фичи языка
** Продвинутая деструктуризация
ClojureScript поддерживает мощную деструктуризацию с вложенными паттернами, значениями по умолчанию и rest-параметрами [[https://clojure.org/guides/destructuring][Associative destructuring also works with lists or sequences of key-value pairs]]

*** Базовая
#+begin_src clojure
(let [{:keys [name age]} user]
  (str name " is " age))
#+end_src

*** Вложенная
#+begin_src clojure
(let [{{:keys [street city]} :address} user]
  (str street ", " city))
#+end_src

*** Со значениями по умолчанию
#+begin_src clojure
(let [{:keys [name age]
       :or {age 18}} user]
  ...)
#+end_src

*** Rest/As
#+begin_src clojure
(let [{:keys [id] :as user} data]
  ...)
#+end_src

** Threading Macros
Threading macros трансформируют вложенные вызовы в линейные потоки данных, улучшая читаемость [[https://clojure.org/guides/threading_macros][This is repeated at each subsequent step with the result inserted as the first argument]]

*** Thread-first (->)
#+begin_src clojure
(-> data
    (filter active?)
    (map :name)
    (take 5))
#+end_src

*** Thread-last (->>)
#+begin_src clojure
(->> users
     (filter :active)
     (map process)
     (reduce combine))
#+end_src

*** Some-> (безопасный для nil)
#+begin_src clojure
(some-> user
        :address
        :city
        str/upper-case)
#+end_src

** Композиция функций
comp создаёт конвейер функций, partial — каррирование. Оба подхода нативны, без лишнего синтаксиса [[http://blog.jayfields.com/2011/01/clojure-partial-and-comp.html][comp function takes a variable number of functions and returns a composition]]

*** comp
#+begin_src clojure
(def process
  (comp validate
        transform
        sanitize))
#+end_src

*** partial
#+begin_src clojure
(def add-10 (partial + 10))
(add-10 5) ; => 15
#+end_src

*** Сравнение с JS
#+begin_src javascript
// JavaScript
data.filter(x => x.active)
    .map(x => x.name)
    .slice(0, 5)

// vs CLJS
(->> data
     (filter :active)
     (map :name)
     (take 5))
#+end_src

* REPL-Driven Development
** Workflow
REPL устраняет цикл компиляции-запуска-отладки: функция пишется, выполняется мгновенно, тестируется с реальными данными [[https://clojurescript.org/reference/repl][One of the reasons that Clojure rocks is that it has a REPL which gives developers the most immediate feedback]]

1. Написать функцию
2. Eval в REPL сразу
3. Тестировать с реальными данными
4. Итерировать без reload

** Процесс демо
- Запустить REPL
- Определить функцию
- Вызвать с тестовыми данными
- Фиксить баги на лету
- Без перезагрузки браузера

** tap> debugging
tap> отправляет данные в REPL для потоковой отладки без console.log [[https://clojurescript.org/guides/faq-js][Macros help you debug without inserting console.log calls]]

#+begin_src clojure
(defn process [data]
  (tap> {:input data})
  (let [result (transform data)]
    (tap> {:output result})
    result))
#+end_src

** Преимущества
- Мгновенная обратная связь [[https://blog.jakubholy.net/2017/12/21/experience-awesome-productivity-with-clojurescripts-repl/][The cycle of problem discovery - troubleshooting - fix is much shorter thanks to the REPL]]
- Нет цикла compile-run-debug
- Сохранение состояния
- Интерактивное исследование
