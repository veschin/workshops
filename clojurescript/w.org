** Что такое фреймворк
любой язык общего назначения дает возможность разработать что угодно.
все ограничивается количеством времени которое нужно инвестировать в тулинг.

есть простые градации тулинга
- модуль. небольшой набор утилити функционала
- библиотека. набор утилити с идеями о том как обрабатывать данные
- фреймворк. набор утилити с
  - философией,
  - готовыми решениями о типовых проблемах, 
  - собственной инфраструктурой
- язык. набор утилити который включает все описанное выше и предлагает мажорные концепции отделяющие его от предшественников. он может быть
  - надстройкой над языком (расширение синтаксиса, например *Typescript*),
  - производным от языка (DSL - мини язык внутри языка, для определенных задач, например *JSX/TSX*)
  - языком паразитом. использовать рантайм существующего языка, например *ClojureScript/Dart/Elm*
** Что такое синтаксис
набор правил, по которому компилятор и программист определяют действия над данными
- идентификатор -  userName
- ключевое слово - if, function
- оператор - +, *, ===
- разделитель - (), {}, ;

фронтенд языка
- композиция правил

бэкенд языка
- парсер (выделяет из сплошного текста ключевые слова)  
- лексер (определяет что делать с ключевым словом)
** Что такое данные и структуры данных
данные - любой набор символов/цифр
вся наша работа - трансформация данных

базовые данные, как правило
- примитивы ~string number~
- структуры ~vector hashmap~ 

примеры того, как из базовых данных составляются сложные данные
- ~data = любая комбинация базовых данных~
- ~object = hashmap~
- ~identificator = резервируемый пользователем string + object ссылка на место в памяти~
- ~operator/keyword = резервируемый языком string~
- ~function = keyword ?identificator + vector/object + ?data~
*** Как бы выглядел JavaScript без синтаксиса, только из данных
#+begin_src js 
let x = 5;
[
    "let", // keyword,
    "=",   // operator
    "x",   // identificator,
    5      // data
] // => identificator

let d = function() { return 42 }; 
[
    "let",             // keyword,
    "d",               // identificator,
    [
        "function",    // keyword,
        [],            // args vector,
        ["return", 42] // body
    ]                  
] // => identificator

d();
[
    d // identificator
] // => data

#+end_src
*** AST (Abstract Syntax Tree)
AST является универсальным языком описания вычислений.
абстрагируясь от синтаксиса, мы получаем переносимость между парадигмами.
функциональная композиция, объектно-ориентированное наследование, потоковые вычисления — всё это становится частными случаями манипуляции древовидными структурами данных.

*** Как выглядит AST на практике
ранее мы показали упрощенное плоское представление. на самом деле AST — это дерево

#+begin_src javascript
// AST для let x = 5;
{
  type: "VariableDeclaration",
  kind: "let",
  declarations: [{
    type: "VariableDeclarator",
    id: { type: "Identifier", name: "x" },
    init: { type: "Literal", value: 5 }
  }]
}

// AST для function() { return 42 }
{
  type: "FunctionExpression",
  id: null,
  params: [],
  body: {
    type: "BlockStatement",
    body: [{
      type: "ReturnStatement",
      argument: { type: "Literal", value: 42 }
    }]
  }
}
#+end_src

*примечание*: каждый узел имеет тип, а дети — это вложенные узлы.
поэтому AST — дерево, а не плоский массив.

** Почему мутации это плохо
основная проблема бесконтрольного изменения данных - *непредсказуемое состояние*
- сложность параллельной обработки

мы не можем отказаться от мутаций насовсем
но можем свести их количество к логически выделенному минимуму 
** Почему функций и данных достаточно
*Алонзо Черч* и *Алан Тьюринг* примерно в одно время разработали логические модели на которых стоит все программирование по сей день
*** _Черч - "An Unsolvable Problem of Elementary Number Theory" (1936)_
алонзо создал формальную систему в которой все является функцией.
ввёл три фундаментальные операции:
- абстракцию для создания функций,
- применение для их вызова,
- и бета-редукцию для вычислений через подстановку аргументов.

данные представляются как функции, а вычисления — как последовательность редукций.

*** _Тьюринг - "On Computable Numbers" (1936)_
одновременно тьюринг в работе  предложил машину тьюринга — абстрактное устройство с
- бесконечной лентой (памятью),
- читающей/пишущей головкой
- и конечным набором состояний управления.

машина работает по детерминированным правилам:
1. читает символ,
2. изменяет состояние,
3. перемещает головку и записывает новый символ.
   
*** Выводы
оба подхода оказались эквивалентными; то, что вычислимо на машине тьюринга, вычислимо и в лямбда-исчислении.
так родился тезис черча-тьюринга: любой алгоритмический процесс может быть реализован как трансформация данных функциями
- любая вычислимая задача может быть представлена алгоритмически
- состояние это данные
- функции трансформируют состояние
- функции хорошо композируются
- любое производное ПО это комбинация функций и данных
** Почему синтаксис может мешать
ранее мы доказали что любую программу можно написать на любом языке,
и любые вычисления можно выразить через данные и трансформации.
*почему синтаксические ограничения могут быть полезны или вредны?*

синтаксис навязывает нам паттерны мышления
- ключевые слова имеют жесткую привязку к контексту. их нельзя использовать произвольно
- отсутствие синтаксических конструкций в языке лишает нас выразительности
- отсутствие композиции между разными синтаксическими блоками

но синтаксис также
- помогает читать код другим людям
- позволяет компилятору локализовать ошибки
- улучшает производительность через конкретизацию намерений

вопрос не в том, нужен ли синтаксис, а в том
- насколько он ограничивает выразительность?
- какие компромиссы между краткостью и читаемостью?
- где заканчивается помощь и начинается ограничение? 

** чего не хватает JavaScript на уровне языка
JavaScript развивался как язык для браузера, поэтому некоторые концепции были добавлены позже или не добавлены совсем

паттерн матчинг
- Elixir/Haskell: встроенный матчинг на уровне языка
- JavaScript: switch/case + if-else цепочки
- можно через библиотеки, но это не на уровне синтаксиса

продвинутая деструктуризация
- Clojure: деструктуризация векторов, мап, вложенных структур в один шаг
- JavaScript: деструктуризация есть в ES6+, но менее мощная для вложенных кейсов

расширение примитивов
- Kotlin: extension functions для любого типа
- JavaScript: можно через prototype, но это мутирует прототип
- нет безопасного способа добавить метод к примитиву

пайпинг
- Clojure/F#: оператор pipe, данные текут через функции
- JavaScript: появился **pipeline operator** как **proposal**, но не везде

полиморфизм по типу
- Clojure/Java: defmulti/defmethod, перегрузка функций
- JavaScript: одна функция с проверкой типов внутри

*но*: многие ограничения решаются через библиотеки, транспиляцию и эволюцию языка.
каждый год что-то добавляют в стандарте.

** LISP (1960)
*** Исторический контекст
#+begin_quote
LISP возник в 1958 году благодаря Джону Маккарти в MIT как язык для обработки символьных данных и искусственного интеллекта. Его создание стало ответом на ограничение существующих языков, ориентированных преимущественно на числовые вычисления.

Предшественником LISP был язык IPL (Information Processing Language, 1956), разработанный Алленом Ньюэллом, Гербертом Саймоном и Клиффордом Шоу для проекта "Логик-теоретик".

Теоретической основой LISP послужило лямбда-исчисление Алонзо Черча (1936), предоставившее математический аппарат для функционального программирования. Маккарти интегрировал эти идеи с практическими потребностями ИИ-исследований.

LISP стал вторым старейшим высокоуровневым языком после FORTRAN и первым, где код представлял собой данные (гомоиконичность). Это заложило основу функциональной парадигмы и повлияло на множество последующих языков.
#+end_quote

*** Фундаментальные принципы
LISP ввёл концепции, которые спустя полвека стали стандартом индустрии:
- Гомоиконичность: код — это данные, данные — это код
- Рекурсия как основной механизм итерации
- Лямбда-функции (анонимные функции)
- Сборка мусора
- Динамическая типизация

Примеры базовых операций:
#+begin_src lisp
(+ 1 2 3 4) ; => 10
(* 2 3 4)   ; => 24

(append '(1 2) '(3 4)) ; => (1 2 3 4)
(reverse '(a b c))     ; => (C B A)
(length '(1 2 3 4 5))  ; => 5

(mapcar (lambda (x) (* x x)) '(1 2 3 4)) ; => (1 4 9 16)
(filter (lambda (x) (> x 2)) '(1 2 3 4)) ; => (3 4)
#+end_src
** Clojure (2007)
*** Проблема, которую решал Clojure
К 2007 году LISP-семейство языков имело репутацию академических и устаревших:
- Дробленость диалектов (Common Lisp, Scheme, Racket, Arc)
- Отсутствие современной экосистемы
- Проблемы с производительностью
- Сложность интеграции с Java-экосистемой, доминировавшей на enterprise-рынке

Rich Hickey, создатель Clojure, увидел возможность решить эти проблемы:
- Использовать JVM как рантайм (доступ к Java-библиотекам)
- Предоставить современный LISP для практической разработки
- Решить проблемы конкурентности через неизменяемость данных
- Создать экосистему вокруг единого диалекта

*** Фундаментальные решения
**** Неизменяемые структуры данных по умолчанию
Вместо мутаций Clojure предоставляет персистентные (persistent) коллекции:
- Операции создания новых структур
- Эффективное переиспользование памяти (structural sharing)
- Безопасность в многопоточной среде

#+begin_src clojure
(def my-vec [1 2 3])
(def new-vec (conj my-vec 4))

my-vec  ; => [1 2 3]
new-vec ; => [1 2 3 4]
#+end_src

**** STM (Software Transactional Memory)
Clojure решает проблему конкурентности через транзакционную память:
- Атомы (atoms) — изолированное состояние
- Рефсы (refs) — координированное состояние
- Агенты (agents) — асинхронные изменения

#+begin_src clojure
(def counter (atom 0))
(swap! counter inc)
@counter ; => 1
#+end_src

**** Code as Data макросы
Макросы — это функции, которые преобразуют код до компиляции:
#+begin_src clojure
(defmacro unless [condition body]
  `(if (not ~condition) ~body))

(unless false (println "This will print"))
#+end_src
** ClojureScript (2011)
*** Что это и зачем нужен
ClojureScript — это Clojure, компилируемый в JavaScript. Он решает фундаментальную проблему фронтенд-разработки: сложность управления состоянием в браузере.

Фронтенд-разработка традиционно страдает от:
- Многообразия фреймворков (jQuery → Angular → React → Vue → Svelte → ...)
- Неизбежного появления "глупых" паттернов при росте проекта
- Сложности тестирования UI-кода
- Отсутствия унифицированных подходов к управлению состоянием

ClojureScript предлагает альтернативный путь: вместо выбора фреймворка — выбрать парадигму.

*** Архитектура
ClojureScript состоит из:
- Компилятора (cljs.build), который транслирует Clojure в JavaScript
- Google Closure Compiler — для оптимизации и минификации
- REPL (Read-Eval-Print Loop) — интерактивная разработка
- Shadow-CLJS — современный инструмент сборки

Базовая программа:
#+begin_src clojurescript
(ns my-app.core)

(defn greet [name]
  (str "Hello, " name "!"))

(defn main []
  (js/console.log (greet "World")))

(main)
#+end_src

*** Реактивное программирование через Reagent
Reagent — это минимальная обёртка над React, которая использует концепции Clojure:

#+begin_src clojurescript
(ns my-app.app
  (:require [reagent.core :as r]))

(defonce state (r/atom 0))

(defn counter []
  [:div
   [:p "Count: " @state]
   [:button {:on-click #(swap! state inc)} "Increment"]
   [:button {:on-click #(swap! state dec)} "Decrement"]])
#+end_src

Преимущества:
- state — просто atom, никакого бойлерплейта и другой логики 
- Обновление через swap!, единая точка интеграции со стейтом 

*** Практические преимущества
**** Разработка через REPL
Возможность изменять код в работающем приложении без перезагрузки:
- Обновить функцию
- Протестировать её в браузере
- Видеть результат мгновенно

**** Лаконичность
Clojure-код часто в 2-3 раза короче JavaScript:
- Меньше синтаксического шума
- Мощные встроенные функции
- Композиция вместо наследования

**** Надёжность
- Неизменяемость данных устраняет целый класс багов
- Сильная типизация (через spec)
- Чистые функции проще тестировать

**** Компромиссы подхода
LISP и Clojure показывают альтернативный путь
- минимальный синтаксис
- код как данные
- макросы для расширения языка

но этот путь
- сложнее для новичков, привыкших к императивному стилю
- требует изменения мышления
- сложнее найти специалистов

нет идеального решения. только выбор компромиссов.
