## State Management

### Проблема 1: Счётчик корзины покупок

**Описание**: Классическая задача синхронизации состояния между несвязанными компонентами. Счётчик товаров в шапке сайта должен автоматически обновляться при изменении содержимого корзины, которая находится на отдельной странице. Это пример проблемы "prop drilling" и необходимости глобального состояния.

**Связь с воркшопом**: [[file:w1.org::*Неизменяемость и структурное разделение][Неизменяемость и структурное разделение]]

**Сценарий**: Корзина в интернет-магазине. Счетчик товаров должен обновляться в header, а сама корзина - на отдельной странице.

**Требования**:
- Кнопка "Добавить в корзину" на странице товара
- Счетчик в header, показывающий общее количество товаров
- Корзина на отдельной странице с возможностью удаления
- При добавлении товара должен обновиться счетчик в header
- При удалении из корзины тоже обновляется счетчик

**Подсказки по реализации**:
- Используйте `reagent/atom` для глобального состояния корзины
- Применяйте `swap!` для добавления/удаления товаров
- Компоненты будут автоматически обновляться при изменении атома

**Ссылки**:
- [Browser-State Architecture: Shopping Cart Implementations](https://dev.to/spicecoder/browser-state-architecture-a-pattern-driven-exploration-through-shopping-cart-implementations-1gp3)
- [State Management в frontend разработке](https://result.school/media/chto-takoe-menedzhery-sostoyanij-i-zachem-razrabotchiku-ih-ispolzovat)

### Проблема 2: Переключатель темы

**Описание**: Переключение темы оформления - это глобальное изменение, которое должно моментально распространиться на все компоненты приложения. Требуется не только изменить состояние, но и синхронизировать его с localStorage, а также обеспечить реактивное обновление всего интерфейса без перезагрузки страницы.

**Связь с воркшопом**: [[file:w1.org::*REPL-Driven Development][REPL-Driven Development]]

**Сценарий**: Переключатель темы (светлая/тёмная), который должен влиять на весь интерфейс.

**Требования**:
- Переключатель в настройках
- Тема применяется ко всем компонентам
- Сохранение темы в localStorage
- Доступ к текущей теме из любого компонента
- Превью темы в реальном времени

**Подсказки по реализации**:
- Сохраняйте тему в атоме и в localStorage
- Используйте `add-watch` для синхронизации с localStorage
- Применяйте CSS классы через Hiccup атрибуты

**Ссылки**:
- [State Management паттерны](https://habr.com/ru/companies/timeweb/articles/597109/)

### Проблема 3: Система уведомлений

**Описание**: Toast-уведомления должны быть доступны для вызова из любой точки приложения. Система требует управления очередью уведомлений, автоматического удаления по таймеру, и обработки множественных уведомлений. Это классический пример необходимости глобального сервиса с простым API.

**Связь с воркшопом**: [[file:w1.org::*Data-driven подход к UI][Data-driven подход к UI]]

**Сценарий**: Система уведомлений, которая может быть вызвана из любого компонента.

**Требования**:
- Показывать success/error уведомления из любого места
- Автоматическое скрытие через 3 секунды
- Максимум 3 уведомления одновременно
- Закрытие по клику
- Глобальные hotkeys для закрытия всех

**Подсказки по реализации**:
- Создайте атом с вектором уведомлений
- Используйте `js/setTimeout` для автоудаления
- Ограничивайте размер вектора через `take`

**Ссылки**:
- [Toast Notifications Design System](https://carbondesignsystem.com/components/notification/usage/)
- [Top Toast Libraries](https://dev.to/lovestaco/top-4-toasts-the-unsung-heroes-of-user-notifications-5nh)

## UI Patterns

### Проблема 4: Состояние модальных окон

**Описание**: Управление модальными окнами требует координации между множеством компонентов. Окно может быть вызвано из любого места приложения, но его состояние должно быть доступно всем заинтересованным компонентам. Это демонстрирует проблему глобального управления UI-состоянием и необходимость централизованного подхода.

**Связь с воркшопом**: [[file:w1.org::*Композиция функций][Композиция функций]]

**Сценарий**: Модальное окно с формой, которое может быть открыто из разных мест приложения.

**Требования**:
- Кнопка "Открыть диалог" в нескольких компонентах
- Модальное окно в корне приложения
- Закрытие модального окна должно обновить состояние во всех компонентах
- Данные из формы должны быть доступны родительским компонентам
- Несколько модальных окон одновременно

**Подсказки по реализации**:
- Создайте атом для состояния каждого модального окна
- Используйте map для хранения данных различных окон
- Применяйте флаги для управления видимостью

**Ссылки**:
- [Mastering Modal Dialogs in React](https://hackernoon.com/mastering-modal-dialogs-in-react-like-a-pro)
- [4 steps to set up global modals](https://opensource.com/article/21/5/global-modals-react)
- [Dialog Pattern W3C](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

### Проблема 5: Многошаговая форма (Wizard)

**Описание**: Wizard-формы требуют передачи данных между шагами, валидации каждого этапа, и возможности навигации вперёд-назад с сохранением введённой информации. Данные из ранних шагов должны быть доступны на последующих, что создаёт сложную систему зависимостей между компонентами.

**Связь с воркшопом**: [[file:w1.org::*Деструктуризация][Деструктуризация]]

**Сценарий**: Многошаговая форма, где шаги зависят друг от друга.

**Требования**:
- 3-4 шага формы
- Навигация: вперёд/назад/переход к шагу
- Валидация каждого шага
- Данные из шага 1 доступны в шаге 3
- Индикатор прогресса
- Сохранение черновика

**Подсказки по реализации**:
- Храните данные всех шагов в одном атоме
- Используйте деструктуризацию для доступа к данным шага
- Применяйте `assoc-in` для обновления вложенных данных

**Ссылки**:
- [Многошаговые формы: плюсы и минусы](https://lpgenerator.ru/blog/2017/07/12/master-form-wizard-plyusy-i-minusy/)
- [Валидация форм на стороне клиента](https://developer.mozilla.org/ru/docs/Learn_web_development/Extensions/Forms/Form_validation)
- [Как создать многошаговую форму](https://ozh.su/blog/sozdanie-effektivnoj-mnogoshagovoj-formy/)

### Проблема 6: Навигация хлебными крошками

**Описание**: Breadcrumbs должны динамически строиться на основе текущего положения в иерархии данных. Они связаны с роутингом, историей браузера, и текущим состоянием навигации. Это требует синхронизации между URL, состоянием приложения и UI-компонентом навигации.

**Связь с воркшопом**: [[file:w1.org::*Threading macros][Threading macros]]

**Сценарий**: Хлебные крошки для навигации по иерархическим данным.

**Требования**:
- Динамические breadcrumbs на основе текущего пути
- Глубокая вложенность: папка/подпапка/файл
- Клик на breadcrumb возвращает на соответствующий уровень
- Обновление URL при навигации
- Поддержка browser back/forward

**Подсказки по реализации**:
- Используйте `->>` для построения цепочки навигации
- Храните путь в атоме и синхронизируйте с URL
- Применяйте `map` для преобразования данных в UI

**Ссылки**:
- [Designing Effective Breadcrumbs Navigation](https://www.smashingmagazine.com/2022/04/breadcrumbs-ux-design/)
- [Breadcrumb Pattern UX](https://uxpatterns.dev/patterns/navigation/breadcrumb)
- [Навигационная цепочка: Хлебные крошки](https://asuikit.com/v3/breadcrumb)

## Real-time & Performance

### Проблема 7: Поиск и фильтрация

**Описание**: Поисковая строка и отображение результатов часто находятся в разных частях компонентного дерева. Необходимо синхронизировать ввод пользователя с фильтрацией данных в реальном времени, а также интегрировать состояние поиска с URL для возможности шаринга и навигации браузера.

**Связь с воркшопом**: [[file:w1.org::*Безопасная навигация (some->)][Безопасная навигация (some->)]]

**Сценарий**: Поисковая строка в header, которая фильтрует данные в области контента.

**Требования**:
- Поисковый input в header
- Список данных в основной области контента
- Фильтрация в реальном времени
- Сброс поиска из другого компонента
- Сохранение поиска в URL

**Подсказки по реализации**:
- Используйте `some->` для безопасной фильтрации
- Применяйте debouncing для оптимизации производительности
- Синхронизируйте поиск с URL через `js/history`

**Ссылки**:
- [Debouncing и Throttling в JavaScript](https://learn.javascript.ru/debounce-throttle)
- [Virtual Scrolling для больших списков](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API)
- [URL Search Params API](https://developer.mozilla.org/en-US/docs/Web/API/URLSearchParams)

### Проблема 8: Обновления в реальном времени

**Описание**: Совместное редактирование требует синхронизации состояния между множеством клиентов в реальном времени. Необходимо обрабатывать оптимистичные обновления для быстрого отклика UI, разрешать конфликты при одновременном редактировании, и синхронизироваться с сервером без блокировки интерфейса.

**Связь с воркшопом**: [[file:w1.org::*Интероп с JavaScript][Интероп с JavaScript]]

**Сценарий**: Чеклист, где несколько пользователей могут редактировать одновременно.

**Требования**:
- Множество todo items
- Обновления в реальном времени между пользователями
- Локальные оптимистичные обновления
- Разрешение конфликтов
- Синхронизация с сервером

**Подсказки по реализации**:
- Используйте WebSocket для real-time коммуникации
- Применяйте `clj->js` и `js->clj` для конвертации данных
- Создайте локальный кэш с оптимистичными обновлениями

**Ссылки**:
- [WebSocket API Documentation](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)
- [Operational Transform для совместного редактирования](https://en.wikipedia.org/wiki/Operational_transformation)
- [Conflict-free Replicated Data Types (CRDT)](https://crdt.tech/)
- [Optimistic UI Updates](https://rauchg.com/2015/7-gotchas-of-websockets)

## Общие паттерны решения

Все эти проблемы демонстрируют общие принципы, которые решаются с помощью ClojureScript:

### 1. Централизованное состояние
Единый источник правды через атомы предотвращает inconsistencies между компонентами.

### 2. Реактивность  
Автоматическое обновление UI при изменении данных через рективность атомов.

### 3. Инкапсуляция
Скрытие сложности за простыми API через функции высшего порядка.

### 4. Тестируемость
Возможность проверять состояние независимо от UI через REPL.

### ClojureScript преимущества:
- Immutability предотвращает побочные эффекты
- REPL позволяет исследовать состояние в реальном времени  
- Data-driven подход упрощает сложные UI взаимодействия
- Композиция функций делает код более предсказуемым
